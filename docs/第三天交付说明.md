## 二、功能范围与验收条件

**Agent 主题**：记账助手「雪庐小账房」，嵌在第二天的登录后记账页里。

**能做什么**：
- 回答通用记账问题（用简体中文，语气平实）；
- 查询**当前登录用户**某月的收支汇总，并据此作答；
- 在同一个会话内记住上下文（如用户告知的昵称）。

**不能做什么**：不增删改账目、不访问他人数据、不执行命令、不调用外部接口。
指令中明确写了「涉及账目的数字必须来自工具返回值，绝不编造」。

**验收条件**（自测按这些走的，见第五节）：

- 未登录不能调用 `/agent`，请求在进入 Agent 之前返回 401，不产生任何模型调用；
- 登录后能流式收到回复，页面逐字显示而非整段弹出；
- 同一会话两轮对话，第二轮能引用第一轮的信息；
- 问账目时后端工具真实执行，回答的数字与 `/ledger/summary` 一致；
- 退出登录后旧令牌再请求 `/agent` 返回 401；
- 第二天的登录、当前用户、记账等功能全部保持可用。

## 四、技术实现要点

### 后端（Microsoft Agent Framework + AG-UI）

**版本**：Python 3.13.14 · agent-framework-core 1.26.0 · agent-framework-ag-ui 1.8.1 ·
agent-framework-openai 1.18.2 · fastapi 0.162.2 · uvicorn 0.54.0

| 接口 | 方法 | 需要登录 | 说明 |
| --- | --- | --- | --- |
| `/agent` | POST | 是 | AG-UI 端点，返回 `text/event-stream` |
| 其余 8 个 | — | — | 全部为第二天已有接口，未改动 |

**Agent 定义**（`app/routers/agent.py`）：名称 `xuelu-ledger-assistant`，
指令写在 `AGENT_INSTRUCTIONS`，能力边界明确（只读、不编造、不提及凭证）。

**只读工具** `month_summary(month: str | None = None)`：从 SQLite 读取当前用户指定月份的
收支汇总，纯只读。**用户身份来自 `ContextVar`**，由已通过 Bearer 校验的依赖写入；
模型只能决定 `month` 参数，无法指定 `user_id`，前端也传不进来。

**几处刻意的设计**：

- 用 `OpenAIChatCompletionClient` 而不是 `OpenAIChatClient`——DeepSeek 这类 OpenAI 兼容服务
  只实现 `/chat/completions`，不支持 `/responses`，用后者会 404。
- 未配置 `MODEL_API_KEY` 时**不注册** `/agent`，并在启动日志打印可操作提示，
  其余接口照常可用——这是一处刻意的降级，方便无凭证环境复现。
- `MODEL_BASE_URL` 强制 `https`，仅允许 `localhost` / `127.0.0.1` / 容器内 Mock 服务名走 http，
  避免有人把内网服务误配成明文。

### 前端（CopilotKit + Runtime）

**版本**：@copilotkit/react-core / react-ui / runtime 均 1.90.2（v2 API）· @ag-ui/client 1.0.5 ·
React 19.3.1 · Vite 8.3.8 · TypeScript 7.0.2

**三个服务**：

| 服务 | 端口 | 作用 |
| --- | --- | --- |
| web（Vite） | 5173 | 页面 + 把 `/api/copilotkit` 代理给 Runtime |
| runtime（Express） | 4000 | 把 AG-UI 请求转给 Python |
| api（FastAPI） | 8000 | 另一个 Compose 项目 |

**Vite 不是 Runtime**：`vite.config.ts` 里只有 `proxy` 转发，AG-UI 协议实现、
会话管理都在 runtime 进程里。这一点在图和文档里都单独说明了。

**认证传递**：浏览器的 `CopilotKitProvider` 在**每次请求时**现取 localStorage 里的令牌，
加 `Authorization: Bearer`；Runtime 按该请求的 header 构造 `HttpAgent` 原样转发，
**不持有、不缓存任何用户凭证**，也不是「拿一个管理员 token 替所有人调用」。

### 容器与网络

两个独立的 Compose 项目，各自有 Dockerfile 与 compose 配置，互不依赖。

**对接方式：显式共享网络**。

```bash
docker network create intern-day-shared   # 只需执行一次
```

后端容器加入该网络并起别名 `api`，前端 Runtime 用 `http://api:8000/agent` 直连。
**没有使用 `host.docker.internal`**，原因见第八节。

前端 Dockerfile 改为多阶段构建：`web` 目标跑 Vite，`runtime` 目标跑 Node，共用一个镜像的依赖层。

## 七、复盘

**最难理解的概念**：AG-UI 到底是「协议」还是「传输」。

一开始我以为 AG-UI 是个能跑的东西——装上它前端就能和后端说话。读文档时
`SSE`、`text/event-stream`、`WebSocket` 混在一起出现，分不清哪个是 AG-UI、哪个是 HTTP。

**怎么想通的**：用一次真实的 curl 请求把它拆开看。

```bash
curl -X POST http://localhost:8000/agent -H "Authorization: Bearer <token>" -d '{...}'
```

```
HTTP 200
data: {"type":"RUN_STARTED","threadId":"t1","runId":"r1"}

data: {"type":"TEXT_MESSAGE_CONTENT","delta":"2026-11 ..."}
```

三层一下就分开了：HTTP 管「怎么连」（POST、状态码、请求头），
SSE 管「怎么送」（`data: {...}` 分帧、响应不结束），
AG-UI 管「说什么」（`type` 字段表示发生了什么）。
AG-UI 规定语义，SSE 是承载它的管道，两者是堆叠关系不是替代关系。
全程没有 WebSocket——没有 upgrade 握手，就是一次普通 POST，响应没结束而已。

**定位过的问题**：容器里调 Agent 一直 401，但同一令牌在宿主机上正常。

**现象**：浏览器点发送，Agent 面板转圈后报错。但页面本身的记账功能完全正常，
`/ledger/entries`、`/ledger/summary` 都是 200。Runtime 日志报
`HTTP 401: {"detail":"登录状态无效，请重新登录"}`，而后端日志里**根本没有 `/agent` 请求**。

**怎么定位的**（四步）：

1. **先确认令牌没问题**：在宿主机上用同一令牌 curl `/agent`，返回 200。
   说明问题不在令牌也不在后端鉴权逻辑。
2. **怀疑 Runtime 没传 header**：在 `runtime.mjs` 的 `agents` 回调里临时加日志，
   输出 `auth = Bearer len=50`（= `"Bearer "` 7 位 + 43 位令牌）。
   说明 Runtime 拿到了正确的 header，也正确构造了 `HttpAgent`。
3. **关键对照实验**：既然 Runtime 拿到了正确 header，就在容器里直接发请求，绕开业务代码：

   ```bash
   # 从 runtime 容器 → host.docker.internal
   node -e "fetch('http://host.docker.internal:8000/auth/me',{headers:{Authorization:'Bearer '+TOKEN}})"
   # → 401

   # 从宿主机 → 同一后端
   curl -H "Authorization: Bearer $TOKEN" http://localhost:8000/auth/me
   # → 200
   ```

   **同一令牌、同一后端、同一接口，只有网络路径不同，结果一个 200 一个 401。**
4. **换个地址验证假设**：用 Docker 网关 `172.19.0.1:8000` 代替
   `host.docker.internal:8000`，返回 **200**。确认是这条路径丢了 header。

**根因**：本机 Windows + Docker Desktop 环境下，容器经 `host.docker.internal`
访问宿主机时，请求被本机代理接管，`Authorization` 头在转发中丢失。
后端收到无凭证请求，返回 401。这不是代码 bug，是环境差异。

**如何解决**：不用绕过的方式，而是换一个更正确的拓扑——两个 Compose 项目通过
**显式共享网络**对接，Runtime 用服务名 `api:8000` 直连，不经宿主机端口。
改完后 `/auth/me` 与 `/agent` 都恢复正常。

**这个问题的价值**：它证明「前端隐藏入口」不等于安全——真正拦住未授权的是后端 401，
而这次 401 是网络层就把凭证弄丢了，说明凭证传递路径必须逐段验证。
另外任务说明特意强调「不能假定对方服务名天然可解析」，我一开始正是按
「用 `host.docker.internal` 就行」写的，结果踩了坑。

**还有什么不理解**：

1. AG-UI 的 `state` 与 `forwardedProps` 的边界在哪。目前 `state` 传空对象能跑通，
   但不确定什么样的 UI 场景真的需要它，想找一个用了 `state` 的官方例子对照读。
2. 适配包里的 `snapshot_store`（`AGUIThreadSnapshotStore`）和「要不要自己做历史持久化」
   的关系。启用它是不是就不用手写会话历史表了？存储后端、清理策略、
   与登录用户的绑定方式都还没弄明白。
3. `authorization_scope_resolver` 的返回值具体影响什么。我返回 `ag-ui:user:{id}` 能跑通，
   但不确定这个 scope 是隔离快照、隔离 detached run，还是两者都有。

## 八、已知问题与限制

**本节说明有意为之的取舍和任务范围外的部分，不是遗留缺陷。**

**有意为之的取舍**：

- **会话历史不落库**：历史存浏览器，每次运行全量上传；刷新页面或服务重启后丢失。
  这是任务说明允许的取舍，README 已写清行为。`threadId` 只是会话分组标签，不是凭证。
- **前端用 Vite 开发服务器演示**：容器里跑 `pnpm dev`，不是生产构建产物。
- **单 Agent、单只读工具**：主题聚焦，符合任务要求的最小能力集。

**任务范围外（明确不做）**：多 Agent、RAG、向量数据库、MCP、复杂审批流、生产部署。

**环境相关的说明（已解决，留档备查）**：

- **`host.docker.internal` 丢失 Authorization**：详见第七节。已改为共享网络直连服务名。
- **容器内 npm 源被拦截**：本机访问 `registry.npmjs.org` 被代理拦（证书链 `UnknownIssuer`），
  `.npmrc` 指向 npmmirror；`--frozen-lockfile` 的完整性校验仍生效。
- **改过 `SEED_PASSWORD` 后登录失败**：种子账号只在账号不存在时创建，不更新已有密码，
  而数据在命名卷里。需 `docker compose down -v` 重建，README 已提醒。
- **GitHub 推送走 WSL**：本机 Windows 侧 `github.com` 的 HTTPS 出口被代理拦住（CONNECT 502），
  只有 SSH 通，因此推送在 WSL 里用 SSH 完成，`origin` 配置为 SSH 地址。
